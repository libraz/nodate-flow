# 概要

nodate-flow は、タスクを行ではなくプロセスとして扱う、自前ホスト型のタスク基盤です。タスクの状態は、依存関係、制約、追記専用のイベントログから導出されます。LLM と MCP は実行経路の一部で、人間と同じイベントを読み、同じ規則に従って書き込みます。

## 名前について

「nodate」は、締切に振り回されない働き方を指す "no date" と、野外で急がずに茶を点てる野点（のだて）の掛け言葉です。

## タスクの状態が決まるしくみ

- **制約**: タスク間の依存関係と制約ルールが、タスクをいつ開始でき、いつ完了できるかを決めます。
- **イベント**: すべての変更は `events` テーブルの 1 行で、変更と同じトランザクションで追加されます。行為者はユーザー、AI エージェント、またはワーカーのようなシステムのいずれかです。
- **導出される状態**: タスクの状態はイベントから計算されます。`derived_state` を直接更新しようとするとデータベースのトリガーが拒否し、制約が認めない遷移はエラーとして返され、適用されません。
- **制約の判定**: 制約に影響しうるイベントが書かれると、制約を評価し直します。タスクが遷移・完了・削除されたときは、それに依存するタスクも評価し直します。判定が変わると `task.constraint.satisfied` または `task.constraint.failed` のイベントが追加されるので、タスクが着手できるようになった理由や止まった理由がタイムラインに残ります。
- **レビューゲート**: 完了ポリシーによって、レビュアーが承認した提出がないと完了できないようにできます。ハンドオフもタスクに記録されます。

UI もこの設計に沿っています。flow-web はステータスを変えるボタンではなく、流れそのものを見せます。プロジェクトごとのボード、リスト、依存関係グラフ、スプレッドシート、タイムライン、ガント、ウィジェットのダッシュボード、タイムラインとアクティビティログをまとめた履歴、AI のアクティビティログがあります。レンズは絞り込んだビューを保存する機能で、公開リンクを使って読み取り専用で共有できます。プロジェクトはアーカイブでき、復元するまで選択肢に出なくなります。画面ごとにヘルプがあり、新しいワークスペースはオンボーディングのチェックリストから始まります。

## シグナルと判定ループ

外部からの入力は、`signals` テーブルの行として入ります。入力元は GitHub、Slack、Google の Webhook、Discord のプレゼンス、カレンダーイベント当日の到来、手動で入力したメモです。シグナルの種別は `signal_kinds/*.yaml` で定義され、既定の自律度もそこで決まります。

シグナルは 3 つの段階を通ります。

1. 決定的なマッチャーが、ワークスペースの設定、種別、対象でシグナルを絞り込み、判定の実行を始めるかどうかを決めます。
2. `signal_judge` 種別のエージェントとして動く LLM の判定器が、ワークスペースの文脈つきでシグナルを読み、確信度つきの判定結果を返します。判定器は何も書き込みません。
3. 決定的なアプライヤーが、判定結果をイベント、下書き、提案のいずれかに変換します。

判定器自身は何も書きません。アプライヤーが書いたイベントには、判定器のエージェントが行為者として記録され、原因となったシグナルへの参照が付きます。自動完了と遡及下書きは別のイベント種別なので、UI がそれを区別して表示でき、ユーザーは下書きをキューとして確認できます。

自律度は `suggest`、`draft`、`auto` のいずれかで、ワークスペースとシグナル種別ごとに、次の順で決まります。種別が完全に一致するルール、`*.presence` のような種別パターンのルール、ワークスペースの既定ルール、ワークスペースの確信度しきい値、最後に種別 YAML の既定値です。flow-worker のシグナル保持ジョブは、期限が切れて一度も適用されなかったシグナルを削除します。

ゲートウェイのプロセスが必要なのは Discord のプレゼンスだけです。運営者がそれぞれ自分の Discord サーバーで自前のボットを動かし、ユーザーは連携設定で自分の Discord アカウントを紐づけます。ゲートウェイの接続方法は [アーキテクチャ](architecture.md) にあります。

## タスクで動くエージェント

タスクに割り当てられたタスクエージェントは、考えたことを書き留めるだけでなく、そのタスクに対して操作できます。操作は、コメントの追加、優先度の変更、期日の変更、状態の変更、サブタスクの作成の 5 つです。管理者が操作ごと、エージェントごとに、不可・承認・自動のいずれかを設定します。不可の操作は実行されません。

承認とは、エージェントが書き込む代わりに提案を出すことです。提案はタスク画面に表示され、タスクを編集できる人が承認または却下します。承認したときに、対象の値が提案時から変わっていなければ適用されます。その間に誰かが値を変えた場合や、提案が期限切れになった場合は、何も適用されません。

自動に設定した操作が承認なしで実行されるのは、エージェントへの付与、エージェントを割り当てた人、実行を起こした人の 3 者がいずれもその操作を許されているときだけです。1 つでも欠ければ、その操作は提案になります。エージェントは非公開タスクでは動きません。

書き込みはすべて、人の編集と同じコードを通り、イベントログと監査ログにエージェントの名義で記録されます。エージェントのコメントは人にメンションせず、コメント内の画像はリンクとして表示されます。1 回の実行には、手数、書き込み数、予算の上限があり、過去の実行の手順はタスクの実行履歴で確認できます。

## AI と MCP

LLM の呼び出しはすべて 1 つの経路を通るため、コストの上限、呼び出しログ、ワークスペースごとのプロバイダー選択がすべての呼び出しに適用されます。プロバイダーはワークスペースごとに設定します。OpenAI、Anthropic、Google、Ollama（API キーの有無を問わず）、または OpenAI 互換のエンドポイントを使えます。1 日の予算とリクエストレートの上限で支出を抑えます。AI 機能を使うには、ワークスペースの設定でプロバイダーを設定する必要があります。

AI 機能は次のとおりです。

- 自由な文章からのスマートなタスク作成
- 状態の推定と優先度の提案
- タスクの埋め込みで順位を付けた、タスク間の関連の提案
- 指示を添えることもできる、タスクの手順の提案
- レンズにコンパイルされる自然言語のコマンドとクエリ
- 受信トレイのトリアージと週次ダイジェスト
- ページの下書き生成
- API から使える、タスクへの返信案とワークスペースのタスクダイジェスト

提案には、承認、編集、却下の操作が付きます。どの提案を自動で適用してよいかは、ワークスペースごとの自動アクションルールが決めます。

flow-api は MCP のエンドポイントも提供します。エージェントや外部ツールは、スコープ付きのワークスペーストークンで認証します。すべての呼び出しにレート制限がかかり、記録されます。外部サービスは個別の連携コードではなく、UI と同じ ACL とイベントログを通してワークスペースの中で動きます。

## カレンダー

flow-web には、flow-api が提供するカレンダーが含まれています。共有カレンダーと個人カレンダー、繰り返しイベント、RSVP つきの参加者、招待、リマインダー、チェックリスト、コメント、添付ファイル、公開共有ページと埋め込みページがあります。タスクはカレンダーイベントにリンクでき、タスクからイベントを作ることもできます。祝日は国ごとに利用できます。カレンダーを使うのに他のプロダクトは必要ありません。

## nodate-time

[nodate-time](https://github.com/libraz/nodate-time) は、独自のリポジトリ、バックエンド、デプロイを持つ別のカレンダープロダクトです。どちらのプロダクトも、相手のコードに依存しません。

どちらも、任意で同じ MySQL データベースに向けられます。その場合、公開されたスキーマ契約を通してユーザー、グループ、カレンダーのデータを共有します。契約は `sql/core/` の core 層と `sql/core/PROTOCOL.md` のプロトコルです。各層の構成と、各プロダクトが契約に対して負う義務は [アーキテクチャ](architecture.md) にあります。

## 行とステータスで管理するタスクツールとの違い

多くのタスクツールは、タスクを人がステータスを更新する行として保存します。モデルが単純で、どの変更も直接的になる一方、ステータスが変わった理由はシステムの外に残ります。

nodate-flow では、状態は制約とイベントログから導出され、LLM は記録される行為者として動き、外部サービスは個別の連携コードではなくシグナルとして入ってきます。その代償として、ステータスを自由に設定することはできません。意図は遷移、制約、イベントで表し、いくつかの不変条件はデータベースの中にあるため、アプリケーションのコードより原因を追いにくくなります。

## ステータスと制約

- このプロジェクトはアルファ版です。最初の安定版までは後方互換性を保ちません。core 層と time 層のスキーマにはデータを保つ upgrade があり、flow 層は移行ではなく再構築で更新します。
- 第三者によるセキュリティ監査は受けていません。脆弱性の報告は `SECURITY.md` の手順に従ってください。
- 動作するインポートコネクターは CSV だけです。他の取り込み元のジョブは受け付けられますが、失敗として終了します。
- flow-api と flow-worker は、既定では単一インスタンスでの動作を前提にしています。レプリカを増やすには、イベントストリームとレートリミッターを、共有の Redis 互換ストアに移します。
- ライセンスは AGPL-3.0 です。改変したバージョンをネットワーク越しに提供する場合は、そのソースを公開する必要があります。
